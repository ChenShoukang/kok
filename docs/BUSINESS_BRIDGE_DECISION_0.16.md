## 口径与限制

- 每次产品业务调用仍是新进程；“后续”不是常驻服务的热请求。首次观察不等于清空操作系统磁盘缓存后的冷启动。
- 纯规则与 JSON 微测量在开发 Node 和源码模块内进行；相同 Node 版本也不代表与打包模块的成本完全一致。
- 子进程诊断包装只用于本脚本，没有修改生产 worker 或增加产品接口；阶段计时不能直接相加当作完整墙钟分解。
- 峰值是本次样本记录，较大输入也只是明确的合成情形，不代表所有输入、所有机器或内存上限认证。

## 为什么保留现状

已确认单次本地桥成本主要在进程生命周期与模块加载，JSON 和规则本身很短；宿主已有当前计划缓存，避免相同要求反复启动纯计划计算。常驻原型有减少这段启动成本的可能，但会引入持续内存、进程管理、通信损坏与恢复成本。

当前没有成对的完整任务证据证明它带来的最终收益足以承担这些成本，因此本批不为约 59 ms 的单次微测量增加常驻服务。需要优化时，先从任务时间线定位重复桥调用和可批量的纯计算，再决定是否验证常驻原型。新的实际文件写入或外部作业不能随重启重放。

本次完成的是测量和保留决定，不宣称达到“整体提效 20%”，也没有用这份微测量替代完整两轮任务与旧任务/取消/恢复门槛。
