# kok 同类差距与实施路线 · v0.9.0 工作区复核

[项目首页](../README.md) · [路线图](../ROADMAP.md) · [文档目录](README.md)

> 本页是实施前的差距基线，保留当时判断与未实施清单。后续实现及验证以 [v0.9.0 功能指南](LIBRARY_0.9.0.md)、[当前验证](VALIDATION_0.9.0.md)与[路线图](../ROADMAP.md)为准。

复核日期：2026-10-30（Asia/Taipei）。对象是本地工作区：`package.json` / Assembly 为 0.9.0，HEAD 为 `c1e078f`，包含未提交改动。本页记录代码阅读、既有验证资料及公开来源对照；本轮没有构建、运行桌面测试、调用模型或实操竞品。下文的里程碑、接口和验收数字均为建议，未实现部分不属于现有功能，也不是发布日期承诺。

建议继续围绕“本地媒体与知识库，把有来源的资料变成可审核的结果”发展。当前最值得投入的主线是：**任务质量基线 → 可更新、有定位的内容索引 → 混合检索 → 导出与恢复 → 随手采集 → 对外工具接口**。资料整理、阅读、摘录与 Agent 可以共用这些基础。

## 1. 先修正上一份意见

| 原判断 | 本次复核后的表述 |
| --- | --- |
| Agent 已经领先、内核不再是瓶颈 | 审批、回执、撤销和来源失效机制有价值；实际任务成功率仍是优先问题。现有证据不足以给竞品排位或宣称领先。 |
| 没有真实模型评测 | 已有历史六例、三例定向复测和两项运行能力实测；缺的是当前 0.9.0 同一构建上的完整复验与更广任务集。见第 3 节。 |
| 没有数据导出 | 已有 JSON 快照导出，包含资料、工作区及操作历史；还缺面向其他软件的 Markdown / JSON 契约、用户可操作的恢复和路径重连。 |
| 没有工作流 | 已有可编辑配方、执行检查点和内置 Agent 技能；缺的是按实际任务扩展可靠性，不能从零计数。 |
| 没有语义能力 | 已有模型生成的上下文摘要；资料库与记忆检索仍以文本匹配为主。**语义压缩和向量检索是不同能力。** |
| 语义索引只需加一个 embedding 模型 | 还需要正文覆盖、分块、定位、增量更新、模型版本、失效清理、范围过滤和效果评测。否则会把旧内容或错误范围的内容搜回来。 |
| 竞品没有“媒体＋锚点＋Agent”的等价物 | 这可以作为 kok 的定位假设。竞品已有媒体、引用和 AI 操作的不同组合，无法凭本次调研证明独家。 |
| 把资料库放进同步盘即可 | 活动数据库不应直接交给文件同步器覆盖；先设计一致性快照、恢复和单写者规则。见第 6 节。 |

仓库有 [MIT 许可](../LICENSE)，不应沿用早期报告中的“闭源”描述；公开发行状态需要单独核实。

## 2. 对比坐标与来源边界

比较对象为个人知识与资料管理产品。通用 Agent 框架可用于参考工程机制，不作为媒体库、采集或阅读体验的直接排名。产品本体、第三方插件、实验特性和历史版本分别标注。

## 4. 差距清单：按用户损失与依赖排序

“已实现”只指找到代码；“部分”指已有机制但缺完整流程；“尚缺”指本次未找到对应实现；“待验证”指存在代码或历史记录，当前效果未建立。优先级是本次建议。

| ID | 优先级 / 状态 | 用户会遇到什么 | 下一步及完成标准 |
| --- | --- | --- | --- |
| G01 | P0 / 待验证 | Agent 能执行，但可能耗尽轮数，或给出带引用的错误结论 | 当前构建复跑旧案例；加入结果读回、数值断言与人工语义复核，形成可复现质量基线。 |
| G02 | P0 / 部分 | 找不到尚未提取的 PDF 正文或独立摘录；不知道哪些资料可搜索 | 统一正文 / 字幕 / 摘录分块，保留页码、章节、偏移或时间；显示覆盖、跳过原因与提取失败。PDF 文字层先于扫描 OCR。 |
| G03 | P0 / 部分 | 文件在外部改了，搜索可能仍用旧正文 | 内容、笔记、摘录、字幕修改触发增量更新；删除和转私密清理派生索引；可取消、重建与恢复。 |
| G04 | P0 / 尚缺 | 换一种说法找不到内容；Agent 的查找也受影响 | 本地 embedding＋FTS5 混合召回；先按资料范围过滤，再选 top-k；同一排序接口服务搜索界面和 Agent。 |
| G05 | P0 / 部分 | 有备份文件，却不知道能否恢复、换电脑是否丢关系 | 版本化恢复清单和恢复预检；Markdown / JSON 互操作导出；保留 ID 与关系，支持路径根目录映射和缺失文件报告。 |
| G06 | P1 / 部分 | 从网页保存文字、图片很绕，下载器也不能代替文章剪藏 | 先定义收件箱与采集数据契约，再接浏览器选区 / 网页正文 / 图片；保留 URL、标题、时间、附件和重复检测。 |
| G07 | P1 / 尚缺 | 扫描 PDF、截图仍搜不到 | 可选本地 OCR；按页保存识别来源、引擎版本与位置。人工修正文与原件分开，结果接入 G02–G04。 |
| G08 | P1 / 部分 | 批量 AI 整理难判断质量，标签可能越来越乱 | 在现有 AI 分类 / 标签基础上做候选列表、差异预览、同义标签建议与按项拒绝；应用与撤销都检查当前版本。 |
| G09 | P1 / 尚缺 | 使用其他 Agent 时无法直接利用 kok 的库 | 先提供本地只读 MCP server：查资料、读片段和来源；写入后续只创建提案，通过现有审批路径执行。 |
| G10 | P1 / 待验证 | 内置 fixture 通过，真实 MCP 服务仍可能接不通或超时 | 建第三方兼容表，覆盖 schema、长结果、取消、断线与重连；核实解释器脚本变化后的授权失效边界。 |
| G11 | P1 / 部分 | 改名 / 移动文件后链接失效；重复导入相同内容难整理 | 先做缺失文件检测和带预览的重连，再做精确文件去重；感知相似图片另作后续能力，避免把两者混为一谈。 |
| G12 | 发布前 / 部分 | 页面、程序诊断与包的版本不一致，用户难判断拿到什么 | 统一版本来源；当前诊断与 MCP clientInfo 仍硬编码 0.8.2。当前候选包重跑、文档对应指纹、远端 CI 实际运行后再报告。签名 / 更新渠道单独安排。 |
| G13 | P2 / 尚缺 | 手机无法随手存、换设备阅读中断 | 先有可恢复快照 / 单写者交接，后续评估只读浏览与移动采集；多端实时编辑成本更高。 |
| G14 | P2 / 部分 | 智能集合条件不够，无法组织某些结构化任务 | 从实际筛选需求补组合条件和保存视图，再决定是否增加自定义字段；不必先做完整块数据库或查询语言。 |
| G15 | P2 / 部分 | 外部研究、图片含义搜索、定时回顾还不完整 | 联网研究依赖来源记录与权限；多模态检索依赖索引与独立评测；定时任务依赖失败恢复和通知语义，分别迭代。 |
| G16 | P1 / 待验证 | 资料量大时可能只有部分内容参与关联，功能数量不等于覆盖率 | [知识索引](../src/Knowledge.cs)有最多 2,000 份资料与总正文预算等限制。大库要显示截断 / 未索引状态，分规模测启动、导入、查询、取消、内存和磁盘增长，再确定容量承诺。 |

AI 问答、标签、摘要、配方、记忆、子代理和隔离计算已有实现，不再当成“从零新增”的条目。现有能力的覆盖率与可靠性仍需验证。

本轮已校正 README 与路线图的当前工作区版本标记；CHANGELOG、运行诊断与 MCP clientInfo 的统一仍列入 G12，旧版本能力说明与验证记录保留原名称。

## 5. 实施阶段与交付边界

每个阶段先完成所列验收再扩展，避免按功能数量宣布完成。M0 与 M1 的方案工作可同时进行；M3 的格式设计可提前，恢复实现依赖一致性快照与稳定来源 ID。

| 阶段 | 范围 / 交付物 | 复用位置 | 依赖 / 相对工作量 |
| --- | --- | --- | --- |
| M0：质量与版本基线 | 把现有质量回放接入默认检查；当前构建复验旧真实案例；定义 30 个验收任务；登记诊断 / MCP / 文档版本漂移 | `tests/agent-quality*`、`tests/agent-live-eval.cjs`、`tools/test-desktop.ps1`、CI、`AgentCognition.cs` | 无新基础设施；中 |
| M1：内容与来源索引 | 统一块记录、内容版本、锚点；PDF 文字层与摘录纳入；增量队列、覆盖与错误面板；先改善词面结果排序 | `Indexing.cs`、`SqliteStore.cs`、`Workspace.cs`、`Jobs`、`ui/search-index.js` | M0 的测试定义；大 |
| M2：本地混合检索 | 首版只接一个本地 embedding 服务；向量＋FTS 融合、带来源片段、界面 / Agent 同一路径；模型不可用时可用词面检索 | M1 索引、`AgentTools.cs`、`AgentRuntime.cs`、`LibraryToolDefinitions.cs` | M1；大 |
| M3：可带走与可恢复 | 开放格式包、恢复预览、路径映射、清点校验；普通用户可完成导出→新目录恢复 | `Library.Snapshot()`、`WorkspaceState`、SQLite backup、导出动作 | M1 来源模型；M2 非硬依赖；中到大 |
| M4：采集与整理闭环 | 收件箱 / 去重 / 来源元数据→浏览器扩展；复用批量审核，新增按需 OCR | 导入、文档、工作区、Operations；新增独立采集适配层 | M1 / M3 契约；大，扩展和 OCR 分开验收 |
| M5：外部互通与设备连续性 | 只读 MCP server；第三方客户端实测；此后再试单写者快照交接 | ModuleRegistry、M1 / M2 检索、M3 快照与恢复 | MCP 读服务依赖 M1 / M2；设备交接依赖 M3；大 |

工作量是相对判断，不是工期估计。每阶段的实现、界面、迁移和测试都包含在交付范围内。发行一致性贯穿各阶段，不能留到最后一个功能之后才补。

### M0 的质量验收建议

先原样复跑历史案例并保留结果，再扩到 30 个任务。建议覆盖：检索与有依据问答 10 个、审核式修改与撤销 8 个、缺失 / 变更 / 中断 / 注入 8 个、计算 / 委派 / MCP 4 个。模型版本、提示、资料、预算和源码 / 运行指纹一起记录；固定任务失败后改提示的结果另建记录，避免只保留最好一次。

分别记录正确完成、诚实部分完成、假完成、越权修改、引用是否支持主张、人工干预次数、耗时和请求 / token 用量。价格未配置时费用显示“未知”。对数字和字段用确定性检查，对概括与引用对应关系做人工抽查；模型评审只作为辅助。

建议首轮交付门槛：确定性状态回归通过；30 个固定任务至少 27 个达到事先定义的预期结果，应当完成的任务不能以部分完成计通过；固定集内假完成和越权修改均为 0；旧失败案例给出当前构建结果。历史四请求条件保留，同一任务若另测更高预算则分栏报告。未达门槛时记录失败、修复或缩小承诺范围，不能只增加预算后覆盖原成绩。27/30 是建议的开发验收目标；小样本结果不推断总体成功率，也不与竞品单次演示比较。

### M1 / M2 的检索设计建议

建议块记录包含：`itemId`、`chunkId`、内容类型、正文、来源锚点、来源版本、提取器版本；向量另带模型标识、维度和分块版本。原文修改与派生索引建立明确映射，旧向量不能因模型名称相同就沿用。

首版优先通过 [Ollama `/api/embed`](https://docs.ollama.com/api/embed)接本地模型，将 embedding 配置与聊天模型分开。内置 ONNX 可以后续评估；先用中文 / 混合语料测效果、内存和包体积。初版不必同时引入多个推理后端或外部向量数据库；SQLite 存储向量、受范围约束的精确计算能否满足目标规模，先测再决定是否增加索引扩展。

词面与向量结果建议按名次融合，例如 RRF，不直接相加两种不可比原始分数。保留精确文件名 / 标识符命中的优先性，返回匹配片段和锚点，按文件折叠重复块。重排模型留到基线显示需要时。

建议准备 40 个有相关来源标注的检索查询：精确词、中文改述、跨语言、字幕时间点、摘录、无答案。对有答案子集报告 `Recall@10 = 前十结果找回的相关来源数 / 标注相关来源总数`，对无答案子集单独报告错误相关结果。比较同语料 FTS / 向量 / 混合，保留开发集与留出集，防止只针对例子调参。门槛是改述召回改善、精确查找不退化、范围外与已失效来源结果为 0；延迟和内存按机器、块数、冷 / 热状态记录后再定阈值。

纯净模式沿用现有禁止 AI 请求的约定，不因模型位于本机就绕过策略；私密数据不进入普通库索引或 embedding 请求。模型停用、资料移除、改要求和切库后，查询与缓存也必须遵循当前范围。

### M3 的数据契约建议

把三个用途分别交付：跨软件互操作导出、一致性备份、用户可执行的恢复。现有快照导出继续保留，新增开放格式不能冒充完整备份。

建议导出包包含 `manifest.json`（格式与版本、ID、校验值、原件引用 / 包含方式）、`notes/*.md`、摘录与锚点 JSON、空间 / 标签 / 关系 JSON、可选附件及缺失清单。正文里的内部链接要有可读替代与稳定 ID，避免导出后只剩 kok 专用地址。凭据、连接环境变量和默认不选中的 Agent 私有记录不混入通用包。

恢复在空白隔离目录预检，检查格式版本、重复 ID、附件哈希、缺失原件和关系；用户确认根目录映射后再写入，失败不覆盖现有库。首版先支持恢复到新库，再评估合并。验收要实际证明笔记内容、摘录坐标、关系、中文文件名、同名文件及缺失文件情形；导出前后原件哈希不变。

### M4 / M5 的接口建议

采集首版可先做应用内“粘贴文字 / URL 保存到收件箱”，这只能覆盖快速记入，不能宣称完成网页正文剪藏。浏览器扩展随后提供网页正文、选区和图片；保留来源与抓取时间、可选离线附件、入库状态和失败重试。扩展入口复用原生导入与操作层，避免再造一套写入逻辑。

MCP server 与现在的 MCP client 是两个方向。建议首版只公开允许范围内的搜索、分页读取、来源定位及摘录；明确协议 / transport 版本，用实际外部客户端验证。后续写入仅创建可审核提案，复用原生冲突检查与撤销；外部调用结果未知时继续阻止自动重放。

## 6. 同步与后续取舍

单写者并不自动解决跨设备覆盖、附件路径和数据库一致性。建议第一步只做受控快照传输：本机通过 [SQLite backup API](https://www.sqlite.org/backup.html)生成一致性快照，附清单和校验值；另一台校验后导入新库或只读副本。进一步做可写交接时，需要明确代次、设备所有权和冲突副本；仅靠云盘上的锁文件不能保证离线两端不同时写入。[SQLite 文档](https://www.sqlite.org/howtocorrupt.html)说明活动事务期间错误备份 / 恢复的损坏条件；[Zotero 官方同步说明](https://www.zotero.org/support/sync)也区分元数据、附件及活动数据目录。

建议暂后安排完整插件市场、多人实时协作、多层写入型代理、通用操作系统沙箱和全平台客户端。结构化查询、引用格式、发布分享、音频概览及多模态检索按具体用户任务逐项选择，不将所有竞品功能自动纳入必做范围。
