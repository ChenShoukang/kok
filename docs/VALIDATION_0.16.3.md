## 实际链路

新默认 TypeScript 任务在需要时调用 `update_task_spec`，提交当前 `baseRevision`、`userRevision`、最新用户原话 `basis` 和有类型的 `changes`。安全补齐直接生效；与当前验收冲突的复杂取消/替换使用 `propose_task_spec`，先显示实际前后要求，再由本次单独确认生效。LangChain 在工具调用处使用 Zod 校验，宿主通过本地纯业务 worker 再独立校验，再写入 `task.requirements_updated` 事件。

同一份完整 Zod schema 用于 SDK 参数校验和宿主边界校验；宿主不再手工维护第二套完整字段类型。提案工具向模型声明精简的传输对象，通过 Zod `superRefine` 继续执行同一完整校验，避免在每轮请求重复发送两份字段定义。原生端保留版本、范围、日志和执行权威。参考[LangChain 官方工具文档](https://docs.langchain.com/oss/javascript/langchain/tools)及[结构化输出说明](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/structured-output.mdx)。使用工具调用承载中途增量，避免为了获取最终结构化响应而另开一个强制规划回合。

支持用途/受众、文档类型/格式/章节、演示页数、长度及单位、聊天交付、定点编辑、完整阅读、来源子集和代码验证要求。未提及的字段保留。已接受的增量按其对应用户消息顺序重放；切换成果类型时保留未提及的用途、受众和来源子集。明确取消的成果单独记录，模型不能再当作缺项自动添加。

初始清晰要求继续使用已有本地快速路径；模型只在当前要求缺项时提出增量。该工具是可选能力，并不保证模型每次都会正确调用，也不是自动证明用户意图的算法。界面保留用户原话和“模型整理”的标记，实际交付仍检查文件与读取/执行回执。

## 不可放宽的边界

- `baseRevision` 必须等于当前规范版本，`userRevision` 必须是最新用户消息；`basis` 必须是其中实际存在的原句。来源、工具结果或模型自己的文字不能伪装为用户消息。
- 严格 schema 拒绝额外权限、工具、工作区、额度字段；来源 ID 只能来自宿主既有允许范围。明确工具白名单和只读策略继续生效。
- `update_task_spec` 只允许补齐或收紧，不能自行取消成果、改掉明确格式/页数、放宽长度、删必需章节/来源、跳过代码验证或重新添加已取消的成果。
- 已能可靠解释的用户修改先走本地路径；剩余复杂冲突由 `propose_task_spec` 展示真实前后要求。必须有该调用的原生单独确认记录，不能通过模型参数、普通工具开始、批量批准或持续授权替代。
- 批准时重新校验当前规范/用户版本和预览内容；拒绝不改要求，同一用户版本不能重复提交相同的已拒提案。信息不足或意图冲突仍须澄清；没有自动证明任意语义的能力。
- 改要求使旧核对和授权失效；同回合尚未开始的旧写入提案被取代。已执行、被用户拒绝或结果不确定的操作不会被当作成功。

## 恢复与兼容

规范版本为用户要求版本加已应用增量数，二者分别可见。每次更新先持久记录提案与结果；若记录后、工具完成回执前中断，同一调用 ID 恢复时复用原结果，不重复更新。若中断发生在更新已保存、旧提案尚未撤销的间隙，恢复会补做撤销；批准写入前也在同一状态锁内重查，避免刚更新的要求与旧写入同时越过检查。无变化的更新不追加事件或版本；重复无变化的调用受现有进展防护约束。

已单独确认的要求变更仅写任务元数据，支持批准后尚未写更新、更新后尚未写结果这两处中断恢复。此例外只接受对应调用的 `individual_requirements` 确认记录；实际文件或外部服务的写入不因此获得自动重放资格。校验错误与运行故障分别处理，内部错误不会变成“可以通过批准绕过”的冲突。

新事件存储版本为 4。旧事件以加法兼容方式读取，原加密字节不重写。旧任务的 `requirementsVersion=0` 不自动启用结构化工具；任务开始时会清除调用者伪造的更新历史，再由宿主设置版本。

## 效率与验证口径

没有新的固定模型请求，也没有独立规划模型。Zod schema 在纯业务 worker 中按需加载，普通本地规则不初始化这套校验对象；SDK 进程继续复用其已有 Zod。一次本机 12 样本测量，打包业务进程墙钟中位数约 57.5 ms、本地规则中位数约 0.048 ms，零模型请求；与旧约 51 ms 的记录不构成严格受控对照，不能据此宣称整体提效。

已增加 9 项运行时测试（含实际 HTTP/SDK schema 和跨重启接续）及 18 项宿主检查，含仅记录更新事件的崩溃恢复和批准前插入更新的检查。完整运行时 **54 项**通过，原生检查总数 **1423 项**。桌面验证覆盖结构化要求、暂停审批后恢复原调用、实际 DOCX 及缺失章节的定点修复。发布门槛包括 **33 项发行 ZIP 桌面套件**、双 Windows 构建、依赖/隐私/版本/文案检查；远端构建和桌面验收均针对待合并提交再次执行。

新增[3 项定点真实任务](../tests/fixtures/requirements-v0163.json)单列于旧 18 题：自然表达的 Word 材料和中文数字范围、后续自定义章节、清晰任务对照。运行方式：

```powershell
.\tools\evaluate-agent.ps1 -Live -ApiKeyFile '已授权的本机密钥文件绝对路径' -Suite requirements -Round round-1 -MaxRequests 32
```

本次实际使用已授权的 DeepSeek 接口，首轮 3 题用了 17 次请求：Word 自然表达题失败，自定义章节调整和清晰任务对照通过。失败任务把 SDK 临时文件称为 Word 交付，宿主未识别到原始表达中的文件要求，因而没有触发实际 DOCX 验收。

修复采用 Deep Agents 已有的公开中间件：新版本任务不向模型开放 SDK 临时文件写入/编辑工具，也拒绝猜测调用；已有读取和自动缓存能力保留。模型收到当前已识别成果及缺项补齐提示，使用结构化工具声明文件要求后再进入原生创建、审批和回读。旧版本任务保留原工具兼容性。

保持原题、原检查条件复测 Word 题，6 次请求通过，生成一份实际 DOCX，并满足 400–600 汉字和三个指定章节。清晰任务首轮没有调用需求更新工具；未额外强制一个规划回合。累计账本为 **23 次模型请求**，包括失败，未重置。首轮结果为 **2/3**，定点复测为 **1/1**；不能拼成一次完整的 3/3 复测，更不等于两轮或未见素材泛化。

本地证据在 `test-output/evaluation-v0163/round-1/evaluation.json`、`targeted-word-2/evaluation.json`、各题 `requirement-updates.json` 和 `request-ledger.txt`。每版本独立目录，v0.16.2 的 132 次请求和此前账本继续保留。测试密钥只在进程内读取，测试设置与备份在结束时清理。
